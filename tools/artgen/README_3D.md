# 3D sprite pipeline (render3d)

Pre-rendered, lit and shadowed raster sprites for the territory map, replacing the flat vector
buildings. Everything is generated by our own Python code; no external assets.

| File | What it is |
| --- | --- |
| `render3d.py` | The renderer: SDF primitives, materials, lighting, post-processing, WebP output. |
| `gen_sprites3d.py` | The models (one function per sprite) and the command line. |
| `sprites3d_*.py` | Optional extra model files, picked up automatically (see "Adding a sprite"). |
| `sheet3d.py` | Review sheet: old vector art next to the new renders, on grass, at 1x and 2x. |

Needs Python 3.13, numpy 2.x and Pillow. Nothing else, no network.

```
python3 tools/artgen/gen_sprites3d.py                   # all sprites -> app/src/main/res/drawable-xxxhdpi/*.webp
python3 tools/artgen/gen_sprites3d.py castle_t3 farm    # only names starting with these words (bld_/deco_ optional)
python3 tools/artgen/gen_sprites3d.py --png DIR ...      # also keep PNG copies in DIR
python3 tools/artgen/gen_sprites3d.py --sheet out.png    # render, then write the review sheet
python3 tools/artgen/gen_sprites3d.py --jobs 1           # single process (default: 4)
python3 tools/artgen/gen_sprites3d.py --list
python3 tools/artgen/gen_sprites3d.py --selftest         # camera alignment check (see below)
python3 tools/artgen/sheet3d.py out.png [prefix ...]     # review sheet from the WebP files already on disk
```

Output is deterministic: the same sources give byte-identical files (checked with 4 processes and with 1).

## Coordinates and the alignment rule

Models use the units of the old vector art (`iso.py`), so dimensions can be copied from
`gen_buildings.py` / `gen_decor.py`:

- `x`, `y`: grid units. `x` runs right-down on screen, `y` runs left-down. A building plot is `0..4 x 0..4`.
- `z`: "z units" = viewport units straight up the screen.
- Radii of round things in plan (`cyl`, `cone`, `sphere`, `torus` major radius): grid units.
- Arguments named `*_px` (edge rounding, capsule radius, torus tube, flag length): viewport units.

The camera is orthographic with a 45 degree yaw and a 30 degree elevation, which is exactly the old
projection:

```
sx = CX + (x - y) * 14
sy = CY + (x + y - S) * 7 - z
```

| `Scene(kind)` | Viewport | Anchor (CX, CY) | Grid point on the anchor | Output |
| --- | --- | --- | --- | --- |
| `"building"` | 128 x 160 | (64, 120) | (2, 2), i.e. S = 4 | 512 x 640 |
| `"decor"` | 64 x 96 | (32, 80) | (0, 0), i.e. S = 0 | 256 x 384 |
| `"wall"` | 64 x 64 | (32, 48) | (0, 0) | 256 x 256 |

Output is 4 px per viewport unit, lossy WebP with alpha (quality 90, method 6), in
`res/drawable-xxxhdpi/` under the same resource name as the vector drawable it replaces
(`bld_castle_t3.webp`, `deco_tree_oak_a.webp`, ...). `SpriteCache.kt` divides the intrinsic size by the
density, so a 512 px wide xxxhdpi bitmap is again a 128-unit sprite.

Internally the renderer works in an isotropic world space, 1 world unit = 1 viewport unit seen face-on:
`X = x * G`, `Y = y * G`, `Z = z * ZS` with `G = 14 * sqrt(2) = 19.80` and `ZS = 1 / cos 30 = 1.1547`.
Consequences worth knowing: a sphere of radius `r` grid units is `r * 17.15` z units from centre to top;
a wall `h` z units tall is `h * 1.155` viewport units of real height.

**Verified numerically.** `--selftest` (a) compares `render3d.project_grid()` with the formula above for
all three kinds: maximum difference 1.4e-14 viewport units; (b) renders small spheres at known grid points
and locates them in the output image:

```
rendered sphere at grid (0.5, 0.5, z 6): centroid (64.00, 93.00), expected (64.00, 93.00)
rendered sphere at grid (3.5, 0.5, z 6): centroid (106.00, 114.00), expected (106.00, 114.00)
rendered sphere at grid (0.5, 3.5, z 6): centroid (22.00, 114.00), expected (22.00, 114.00)
rendered sphere at grid (3.5, 3.5, z 6): centroid (64.00, 135.00), expected (64.00, 135.00)
rendered sphere at grid (2.0, 2.0, z 70): centroid (64.00, 50.00), expected (64.00, 50.00)
```

Rules that keep a sprite sitting right on the map:

- A building's pad is `box(0, 0, 4, 4, -LIP, 0)` (`building(t)` adds it): its top is `z = 0`, the ground
  plane is `z = -LIP`. Put everything on `z = 0` as in the old art.
- Stay inside the viewport. The CLI prints each sprite's `margin` (distance of the nearest opaque pixel to
  the image border, viewport units) and flags anything under 1. A building may be about 115 z units tall
  at the plot centre, less towards the back corner (`z < 120 + (x + y - 4) * 7 - 4`).
- Keep the footprint on the pad. Roof overhangs and flags may lean a little over the edge, as before.
- The game draws animated effects on top of sprites at fixed building coordinates
  (`TerritoryLife.kt`: `buildingIdle`, `decorIdle`): torch flames on the castle gate and the barracks
  door, chimney smoke on houses, braziers, forge glow. Put the baked torch / chimney at those coordinates.
  `torch(sc, T, x, y, z)` takes the flame centre, the same numbers the Kotlin code uses.

## How the renderer works

1. **Scene** = a list of solids; each is an SDF tree plus one material. Every node knows its bounding box.
2. **Visibility**: each solid is sphere-traced only inside its own screen rectangle and bounding box,
   with rays compacted as they finish; the per-solid depths are merged in a z-buffer. Union between solids
   is therefore free and exact; subtraction and smooth blending happen inside one solid's tree.
3. **Normals** by tetrahedral finite differences of the hit solid's SDF.
4. **Materials** are procedural, evaluated in world space: `albedo(ctx)`, optional `height(ctx)` for bump
   mapping, `emis(ctx)`, plus specular / metal / wrap parameters. `ctx.u, ctx.v` are 2D texture
   coordinates in world units: on walls and roof slopes `u` runs along the face and `v` is height, on flat
   tops `(u, v) = (x, y)`; with `cyl=(xc, yc, r)` the mapping is cylindrical (round towers, cones).
5. **Shadows**: the scene is traced once more from the key light into a depth map; shading uses
   percentage-closer soft shadows (blocker search, then a penumbra that widens with the distance to the
   occluder; tap patterns are rotated per pixel by a hash, so there is no banding and no randomness).
6. **Ambient occlusion**: the whole scene's truncated distance field is sampled on a coarse voxel grid
   (1 world unit); four samples along the normal give the occlusion.
7. **Lighting** in linear light: warm key from the upper left-front (faces looking at `+y` are lit, faces
   looking at `+x` are in shade), cool sky fill and warm ground bounce scaled by AO, a weak cool fill from
   the right so shaded sides keep their form, a little rim light, Blinn-Phong highlights, and a fake
   sky/horizon reflection for metals.
8. **Ground**: pixels that hit no solid become a transparent shadow catcher: cast shadow + contact
   shadow, written as semi-transparent dark pixels and faded out before the viewport border.
9. **Post**: 2 x 2 supersampling (premultiplied), bloom from emissive pixels (windows, torches), ACES-style
   tone curve, sRGB encode, a small saturation / contrast grade, and a gentle dark edge around the
   silhouette (`outline`, 0 turns it off).

All tunables live in `render3d.LIGHT`; a scene can override any of them: `Scene("decor", shadow=0.4)`.

## Modelling API (`render3d`)

```python
sc = Scene(kind="building", ground=0.0, clip=None, **light_overrides)
sc.add(node, material, cast=True, cyl=None, ao=True, visible=True, name="")
img = render(sc, ss=2, px=4)        # PIL RGBA
save_webp(img, path)
```

Primitives: `box(x0, y0, x1, y1, z0, z1, r_px=0)`, `cyl(xc, yc, r, z0, z1, r_px=0)`,
`cyl_x(x0, x1, yc, zc, r_px)`, `cyl_y(y0, y1, xc, zc, r_px)` (horizontal: arches, barrels),
`cone(xc, yc, r0, z0, z1, r1=0)`, `sphere(x, y, z, r)`, `ellipsoid(x, y, z, rx, ry, rz)`,
`torus(xc, yc, z, R, r_px)`, `capsule(p0, p1, r_px)` (poles, rails, branches),
`gable(x0, y0, x1, y1, z, h, axis="x", over=0, thick=1.4)`, `hip(x0, y0, x1, y1, z, h, over=0, thick=1.4)`
(a pyramid on a square plan), `flag(x, y, z, w, h, taper)` (cloth flying to screen-right).

Operators: `union(*a)`, `sub(a, *cuts)`, `inter(*a)`, `smooth(k_px, *a)` (blobby union),
`rounded(a, r_px)`, `move(a, dx, dy, dz)`, `rotz(a, deg, ox, oy)`, `rot(a, axis, deg, pivot)`,
`repeat(a, axis, step, n)` (merlons, posts, rows), `lumpy(a, amp_px, freq, seed)` (foliage, rock).

Materials (all take colours as `"#RRGGBB"`, all have value-noise variation):

| Function | Look |
| --- | --- |
| `m_planks(color, width, horizontal=False)` | rough wood planks / logs |
| `m_thatch(color, row)` | straw thatch in ragged layers |
| `m_plaster(plaster, timber, z0, z1, bay, ox, oy)` | timber frame with plaster infill |
| `m_rubble(color, size)` | irregular field stone |
| `m_stone(color, course, length, joint)` | cut stone blocks with mortar lines |
| `m_tiles(color, row, width, kind)` | roof rows: `"clay"`, `"slate"`, `"scale"`; `metal=` for gilded tiles |
| `m_marble(color, vein)` | white marble with faint veins and ashlar joints |
| `m_gold(color)`, `m_metal(color)` | metal trim with a specular highlight |
| `m_cloth(color, trim=None, stripe=None)` | banners and flags |
| `m_ground(kind)` | pads: `"dirt"`, `"grass"`, `"paved"`, `"marble"`, `"soil"` |
| `m_water(color, deep)` | water |
| `m_foliage(color)` | leaves |
| `m_glow(color, power, bars=True)` | emissive window / flame, feeds the bloom |
| `m_flat(color, noise)` | plain props |

A new material is a `Material(albedo, height=None, bump=1, spec=0, gloss=24, emis=None, metal=0, wrap=0)`
whose callables take a `Ctx`; copy `m_stone` as a template.

### Worked example: a well (0.25 s)

```python
import render3d as r3
from render3d import Scene, capsule, cyl, gable, sub, torus

def well():
    sc = Scene("decor")                                    # 64 x 96, grid (0, 0) is the ground anchor
    drum = sub(cyl(0, 0, 0.62, 0, 8.0), cyl(0, 0, 0.46, 2.0, 9.0))      # outer cylinder minus the shaft
    sc.add(drum, r3.m_rubble("#A39A8C", size=3.2), cyl=(0, 0, 0.62))    # cylindrical texture mapping
    sc.add(torus(0, 0, 8.0, 0.54, 1.3), r3.m_stone("#8F887B", course=2.5), cyl=(0, 0, 0.54))   # rim
    sc.add(cyl(0, 0, 0.46, 1.0, 5.2), r3.m_water(), cast=False)         # water
    wood = r3.m_planks("#6A4326", 0.1)
    sc.add(capsule((-0.55, 0, 0), (-0.55, 0, 21), 0.7), wood)           # posts
    sc.add(capsule((0.55, 0, 0), (0.55, 0, 21), 0.7), wood)
    sc.add(capsule((-0.55, 0, 17), (0.55, 0, 17), 0.5), wood)           # windlass
    sc.add(gable(-0.75, -0.42, 0.75, 0.42, 20, 7, axis="x", over=0.05),
           r3.m_tiles("#B04A32", kind="clay", row=2.4, width=2.4))
    return sc
```

The larger worked example is `castle(t)` in `gen_sprites3d.py`: one function for all five tiers, built
from the shared parts below.

## Adding a sprite

1. Write a function that returns a `Scene`, in `gen_sprites3d.py` or in a new file
   `tools/artgen/sprites3d_<something>.py` (use a separate file when several people work in parallel;
   it only needs `import gen_sprites3d as g` and a module-level `SPRITES = {...}`).
2. Register it under the exact resource name: `SPRITES["bld_sawmill_t2"] = lambda: sawmill(2)`.
   Names must match `res/drawable/*.xml` / `SpriteIds.kt`.
3. Render it with `--png DIR`, open the PNG on a grass background (`#5a9a3c`) and look at it at 1x
   (128 px wide) as well as full size. Check the printed `margin`.
4. When the WebP replaces a vector drawable, delete the `.xml` of the same name. Until then both exist;
   note that Android's resource matching already prefers the `drawable-xxxhdpi` bitmap over the
   unqualified vector on most devices.

Shared parts in `gen_sprites3d.py`:

- `building(t)` -> `(scene, Tier)`: a building scene with the tier's 4 x 4 pad.
- `Tier(t)`: the material set of a tier (1 wood & thatch, 2 timber & clay tile, 3 cut stone & slate,
  4 white stone & blue roofs, 5 marble & gold): `T.wall(...)`, `T.roof`, `T.base`, `T.trim`,
  `T.curtain`, `T.pad`, `T.gold`, `T.glow`, `T.banner`.
- `window(...)`, `door(...)`: add the lit pane / plank leaf and the frame, and return the hole; subtract
  the holes from the wall: `sc.add(sub(box(...), *holes), T.wall())`. Faces are `"L"` (left-front,
  plane `y = f`) and `"R"` (right-front, plane `x = f`).
- `merlon_ring`, `round_tower`, `palisade`, `flagpole`, `banner`, `torch`, `shield`, `fence`,
  `crop_rows`, `haybale`, `windmill`, `weapon_rack`, `dummy`, `chest`.

Things that make a sprite read at game size (a building is 60-130 px wide on screen):

- Split a model into several solids. Each solid is traced only inside its own bounding box, and one
  solid has one material.
- Big shapes first: roof and walls must differ in value and hue; give the roof an overhang (`over`) so
  it throws a shadow on the wall; recess windows and doors with `sub`.
- Albedo is linear and the key light is strong: pale materials wash out. Stone around `#BCB29C`,
  marble around `#EFE9DC`, thatch around `#B0965C` render well; anything lighter goes white on lit faces.
- Put lit windows on both visible faces; the left-front face is in light, the right-front in shade, and
  the glow is what keeps the shaded face alive.
- `repeat` needs each copy narrower than the step. `lumpy`, `flag`, `ellipsoid` and `smooth` are
  inexact distances and march with a safety factor, so keep them to small solids.
- Tiling pieces (walls): see `wall_piece`. Flat cut ends, features that repeat with the piece length,
  `outline=0`, the two neighbours added as `visible=False` phantoms, and `clip=` limiting the baked
  ground shadow to the piece's own cell.

## Speed

Measured on the 4-core dev container, 2 x 2 supersampling, including WebP encoding:

| Sprite | Solids | One process |
| --- | --- | --- |
| wall piece (256 x 256) | 4 | 0.7 s |
| tree / house (256 x 384) | 2-12 | 1.3-2.0 s |
| farm, barracks (512 x 640) | 20-45 | 2.5-3.3 s |
| castle tier 1-5 (512 x 640) | 36-103 | 2.5-4.6 s |

About 40 % of a building's time is WebP `method=6` (1-1.9 s); the render itself is 1.2-2.8 s.
The 16 phase-1 sprites take 42 s on one process and 11-17 s with the default 4 processes, so the
full set of about 150 sprites is a 2 minute batch.
